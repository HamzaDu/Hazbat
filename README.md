# BMAC By HazBAT — Battery Materials & Cells Traceability




Developed by the **Battery Materials & Cells Group**, WMG, University of Warwick.

BMAC is a full-chain traceability database for battery research labs. It tracks every step from raw electrode powder through coating, cell assembly, and electrochemical testing, with every relationship enforced at the database level.

---

## Deployment

BMAC is distributed as a single container image, built from the `Dockerfile` in this repository. The image supports
three configurations.

| Configuration | Database | Intended use |
|---|---|---|
| Development container | PostgreSQL inside the container, recreated on every rebuild | Development in Visual Studio Code |
| Self-contained container | PostgreSQL inside the container, stored in a volume | Deployment without a separate database server |
| Standalone database | An existing PostgreSQL server | Deployment against a managed database |

All settings are held in a single file, `/etc/hazbat/hazbat.ini`. The settings are listed in the reference at the end of
this section.

### Development container (Visual Studio Code)

**Prerequisites:** Docker, and Visual Studio Code with the Dev Containers extension.

**Procedure**

1. Open the repository in Visual Studio Code.
2. Run the command *Dev Containers: Reopen in Container*. The initial build may take several minutes.
3. Open http://localhost:8000. Authenticate with the user name `dev` and the password `dev`. This account has no
   authenticator, so the first login proceeds directly to two-factor enrolment.

**Behaviour**

- The container is built from the repository's `Dockerfile` and runs its own PostgreSQL server.
- The repository is mounted at `/app`, and the server runs with automatic reload. Changes to code, templates and
  static files therefore take effect without a rebuild.
- Settings are read from `.devcontainer/hazbat.ini`, which contains development passwords only.
- The example data in `.devcontainer/db-init/02-dev-seed.sql` is loaded on every start of the container.
- No data is retained across rebuilds. The command *Dev Containers: Rebuild Container* produces a new database, and is
  required after a change to the schema, the `Dockerfile`, `requirements.txt` or `entrypoint.sh`.
- A connection named "Hazbat dev DB" is configured for the SQLTools extension, using the user `hazbat_admin`, the
  password `dev` and the forwarded port 5432.

### Self-contained container

In this configuration the container runs both PostgreSQL and the application.

**Procedure**

1. Build the image:

   ```
   docker build -t hazbat .
   ```

2. Start the container:

   ```
   docker run -d --name hazbat -e START_LOCAL_DB=1 -p 127.0.0.1:8000:8000 \
     -v hazbat-pgdata:/var/lib/postgresql/data \
     -v hazbat-config:/etc/hazbat \
     -v hazbat-uploads:/app/uploads \
     hazbat
   ```

3. Create the first user, who is an administrator:

   ```
   docker exec -it hazbat createsuperuser
   ```

4. Set `base_url` in `/etc/hazbat/hazbat.ini`, within the `hazbat-config` volume, to the address used to reach the
   application, and restart the container. QR codes generated by the application refer to this address.

**Volumes**

| Volume | Mount point | Contents |
|---|---|---|
| `hazbat-pgdata` | `/var/lib/postgresql/data` | The PostgreSQL data files |
| `hazbat-config` | `/etc/hazbat` | The settings file, including the database passwords and secrets generated on first start |
| `hazbat-uploads` | `/app/uploads` | Uploaded cycling data files |

The `hazbat-pgdata` and `hazbat-config` volumes belong together and are to be retained or discarded as a pair.

The prefix `127.0.0.1:` in the port option restricts access to the local host. It is omitted to accept connections on all
addresses.

### Standalone database

In this configuration the container connects to an existing PostgreSQL server. The variable `START_LOCAL_DB` is not set.

**Preparing the database.** The following statements are executed by a PostgreSQL superuser. The administrator role
requires the privilege to create roles and to create objects in the `public` schema.

```sql
CREATE DATABASE bmac;
CREATE ROLE hazbat_admin LOGIN CREATEROLE PASSWORD 'administrator-password';
\c bmac
GRANT ALL ON SCHEMA public TO hazbat_admin;
```

**Settings file.** A directory `config` is created containing a file `hazbat.ini` with the `[database]` settings. The
container creates the read-write and read-only roles, using the passwords given here.

```
[database]
host = db.example.org
port = 5432
name = bmac
admin_password = administrator-password
read_write_password = read-write-password
read_only_password = read-only-password
```

**Procedure**

1. Start the container, mounting the directory and not the single file. The container adds the missing `[app]` settings
   to the file, which requires the file to be replaceable.

   ```
   docker run -d --name hazbat -p 127.0.0.1:8000:8000 \
     -v "$PWD/config:/etc/hazbat" \
     -v hazbat-uploads:/app/uploads \
     hazbat
   ```

2. On the first start the container adds the `[app]` settings, applies the schema in `schemas/` and creates the
   read-write and read-only roles.
3. Create the first user and set `base_url`, as described for the self-contained container.

### Settings reference

| Section | Setting | Description |
|---|---|---|
| `[database]` | `host`, `port`, `name` | Location and name of the database. Written automatically only for the self-contained container (`localhost`, `5432`, `bmac`). |
| `[database]` | `admin_password`, `read_write_password`, `read_only_password` | Passwords of the three database roles. Generated automatically only for the self-contained container. |
| `[app]` | `base_url` | Address encoded in QR codes. Defaults to `http://localhost:8000`, which is suitable for testing only. |
| `[app]` | `session_secret` | Key used to sign session cookies. Generated if absent. |
| `[app]` | `two_factor_key` | Key used to encrypt authenticator secrets. Generated if absent. |
| `[app]` | `max_2fa_interval_hours` | Longest time a user may set between second-factor checks. Defaults to 48. |
| `[app]` | `disable_2fa` | When `true` or `1`, login skips the second-factor step. Written only when the image was built with `NO_2FA`, and never overwritten. Optional. |
| `[app]` | `gemini_api_key` | API key for HAZbot. Optional. |
| `[app]` | `trusted_proxies` | Address of a reverse proxy whose forwarded headers are trusted. Optional. |

Missing `[app]` settings are added at start-up in every configuration. Existing comments in the file are preserved.

### Environment variables

| Variable | Effect |
|---|---|
| `START_LOCAL_DB` | When set, the container runs its own PostgreSQL server. |
| `RELOAD` | When set, the application server reloads on changes to the source files. |
| `SEED_SQL` | Path of an SQL file executed against the local database after the schema is applied. |

### Build arguments

The following arguments are given to `docker build` with `--build-arg`.

| Argument | Effect |
|---|---|
| `PYTHON_VERSION` | Version of Python installed with uv, for example `3.12`. Defaults to `latest`. |
| `POSTGRES_VERSION` | Version of PostgreSQL installed: `16`, `17`, `18` or `latest`. Defaults to `latest`. Any other value is passed to `apk` as the package suffix. |
| `NO_2FA` | When `true` or `1`, the container adds `disable_2fa = true` to the settings file at start-up, and login skips the second-factor step. Existing two-factor records are not changed. |

For example:

```
docker build --build-arg PYTHON_VERSION=3.12 --build-arg POSTGRES_VERSION=16 --build-arg NO_2FA=1 -t hazbat .
```

An existing settings file is never overwritten. To turn the setting off again, set `disable_2fa` to `false` in the file.
Removing the line is not enough while the image is still built with `NO_2FA`, because the line is added again at the next
start.

### Disabling two-factor authentication

**Disabling two-factor authentication is very, very strongly discouraged for any deployment other than testing.** It is
provided only for development and automated testing, where a second factor is an obstacle and the data is not real.

While `disable_2fa` is `true` or `1`:

- Every user, including every administrator, is logged in by a user name and password alone. A stolen, guessed or reused
  password gives full access to the account.
- The setting applies to all users at once. It cannot be set for one user.
- Users are not asked to enrol an authenticator, and the two-factor checks and trusted browsers are not used.

The setting does not delete anything. Existing authenticators and recovery codes are kept, and apply again when the
setting is turned off.

An image built with `NO_2FA` must not be used for a deployment that holds real data or that can be reached from an
untrusted network.

## First start

### What happens

Whatever the way of deployment, start-up consists of three steps, carried out in this order.

1. **Settings.** `scripts/initconfig.py` adds any missing `[app]` settings to the settings file. When the database is
   built into the container (`START_LOCAL_DB`), it also adds the missing `[database]` settings, including generated
   passwords, and creates the administrator role in the local PostgreSQL server.
2. **Database.** `scripts/dbgen.py` applies the files in `schemas/` that have not been applied yet, in name order,
   creates the read-write and read-only roles if they do not exist, and sets their privileges.
3. **Server.** `scripts/serve.py` starts the web server on port 8000.

In a container, `entrypoint.sh` carries out these steps itself, after starting PostgreSQL when `START_LOCAL_DB` is set.
Outside a container they are carried out by hand.

### In a container

No action is needed beyond the commands given under *Deployment*. The first start takes longer than later ones, because
the database, the settings file and the schema are created. Progress is shown in the container's log (`docker logs
hazbat`). A start-up step that fails stops the container, and the log gives the reason.

### Without a container

**Prerequisites**

- Python 3, with the packages installed by `pip install -r requirements.txt`.
- A PostgreSQL server prepared as described under *Standalone database*.
- The settings file `/etc/hazbat/hazbat.ini`. The location is fixed, and the account that runs the server must be able
  to read the file. `scripts/initconfig.py` is intended for containers, because it assumes that it runs as the
  administrative user and that a group `app` exists, so the file is written by hand:

  ```
  [database]
  host = db.example.org
  port = 5432
  name = bmac
  admin_password = administrator-password
  read_write_password = read-write-password
  read_only_password = read-only-password

  [app]
  base_url = https://bmac.example.org
  session_secret = a-long-random-value
  two_factor_key = another-long-random-value
  max_2fa_interval_hours = 48
  ```

  A suitable random value is produced by `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`.

**Procedure.** From the root directory of the repository:

```
python3 -m scripts.dbgen
python3 -m scripts.serve
```

The first command applies the schema and creates the read-write and read-only roles. The second starts the server on port
8000, and ends only when the server is stopped.

### Creating the first user

Until a user exists, the home page displays a notice that the server has not been configured, and the login page
redirects to it. The first user, who is an administrator, is created from the command line:

- In a container: `docker exec -it hazbat createsuperuser`
- Without a container, from the root directory of the repository: `python3 -m scripts.createsuperuser`

The command prompts for a user name, a full name and a password, which is entered twice. If the user name already
exists, the command displays a warning and, on confirmation, replaces that user completely, including the user's API
keys, two-factor settings and project assignments.

At the first login the user enrols an authenticator application: the page displays a QR code and a secret, and eight
recovery codes that are shown once and can each be used once. The login completes when a code from the application is
entered.

## Administration

### Users and access

Every user has a user name, a password, a full name and a role. A user is either an administrator or an ordinary user.
Administrators can see every project. Ordinary users can see only the records of the projects that have been assigned to
them. Materials have no project and are visible to all users.

**First administrator.** The first user is created from the command line, as described under *First start*.

**Passwords** are stored as bcrypt hashes and may not be longer than 72 bytes.

**Two-factor authentication.** Every user authenticates with a time-based one-time password (TOTP). At the first login,
the user enrols an authenticator application and receives recovery codes, each of which can be used once. A user may
choose, on the My Account page, how many hours a browser remains trusted after a successful check. The default is zero,
which requires a code at every login. The longest permitted time is the setting `max_2fa_interval_hours`.

**Each user's own account.** The *My Account* page, in the menu under the user's name, allows a user to:

- change their full name;
- change their password, which requires the current password;
- set the time between two-factor checks;
- reset their two-factor authentication, which requires the current password. The user enrols again at the next login.

**API keys.** The *API Keys* page, in the same menu, creates keys for scripts and other programs. A key is displayed
once, at creation, and an expiry date is optional. A key is sent in the header `Authorization: Bearer <key>`, and has the
access of the user who created it. A key can be revoked at any time.

### User management

Administrators manage users from the *Users* menu.

| Page | Contents |
|---|---|
| All users | A table of all users with their role, projects, two-factor status and whether the account is locked. The search box filters the table by user name and full name without contacting the server. A user name opens the page for editing that user. |
| Create a new user | Creates a user with a user name, password, full name, an optional administrator role and the projects to which the user has access. |

The page for editing a user changes:

- the full name, the administrator role and the project assignments;
- the password, which an administrator sets without knowing the previous one;
- the two-factor authentication, which is reset so that the user enrols again at the next login.

The table also provides two actions on each user:

- **Lock** prevents the user from logging in. Existing sessions end at the next request, and the user's API keys stop
  working. **Unlock** reverses it.
- **Delete** removes the user together with their API keys, two-factor settings and project assignments.

An administrator cannot lock or delete their own account, or remove their own administrator role.

### Project management

Administrators manage projects from the *Projects* menu.

| Page | Contents |
|---|---|
| All projects | A table of projects with their status, the number of records that belong to each and the number of users assigned to each. A project name opens the page for that project. |
| Create a project | Creates an active project. |

A project name begins with a letter or a digit, contains only letters, digits, spaces, dots, hyphens and underscores, and
has at most 60 characters. Names that differ only in capital letters are treated as the same name.

The page for a project shows its status and records and users, and switches the project on or off. An inactive project
is not offered in the lists used when users and records are created. Existing records and users keep it. Projects cannot
be renamed or deleted from the interface.

The schema creates the projects `LEAP`, `FAST` and `Shared`.

## What it does

- **Records** materials, coatings, SLP cells, coin cells, and MLP cells in a relational PostgreSQL database
- **Enforces traceability** — every cell links back to its coating, every coating links back to its material
- **Visualises** the full manufacturing graph interactively, with multi-dimensional filtering and path highlighting
- **Generates lineage & passport cards** per cell, including EU Battery Regulation DPP scaffold fields 
- **Plots cycling data** from BioLogic `.mpr` files: capacity fade, coulombic efficiency, and voltage vs. capacity curves
- **Exports** any table to CSV or Excel

## Data hierarchy

```
tbl_materials
    └── tbl_coating
        └──tbl_cell 
        e.g ├── tbl_slp        (single-layer pouch)
            ├── tbl_coincell   (coin cell, e.g. CR2032 half cell)
            ├── tbl_mlp        (multi-layer pouch — two coatings: cathode + anode)
            └── etc.
```

## Features

### Lineage & passport card
Page for every component showing:
- Full manufacturing traceability chain (material → coating → cell → formation → testing)
- Capacity fade chart and voltage vs. areal capacity curves
- EU Battery Regulation sections: supply chain due diligence, material inputs, recycled content targets, circularity
- Print-to-PDF layout
- JSON export for downstream processing

### Bulk upload
CSV or Excel upload for all five record types. Column names are case-insensitive.

### Certificates of Analysis (COA)
Every material card has a **+ COA** button at the top right, on the New Material page, after a bulk upload and on the material's own card. It takes `.pdf`, `.docx` or `.doc` (up to 25 MB); drop a file on a card, or drop several on the bulk results page and they are matched to cards by the material ID in the file name. Clicking **COA** opens an in-browser preview with download, replace and remove. Word files are converted to PDF for the preview with LibreOffice:

```bash
sudo apt install --no-install-recommends libreoffice-writer   # Word preview (optional)
psql "$DATABASE_URL" -f migrations/001_material_coa.sql       # existing databases only
```
Files are stored in `uploads/coa/<material_id>/` (git-ignored, include it in backups). COAs need a login to view.

### Traceability graph
A full `vis.js` force-directed network of every record and their relationships. Clicking any node highlights its complete upstream (ancestors) and downstream (descendants) path with a pulsing edge animation, and opens a quick-view side panel showing key fields, and QR code.

### Cycling data viewer
Upload a BioLogic `.mpr` file and attach it to any cell record. The graph page and lineage card then show:
- Discharge capacity per cycle (capacity fade)
- Coulombic efficiency per cycle
- Voltage vs. capacity curves, selectable by cycle, normalised by electrode area

## ID conventions

BMAC uses human-readable hierarchical IDs that encode provenance directly:

```
CAT-NMC-001             ← cathode material, NMC chemistry, batch 001
CAT-NMC-001-C001        ← first coating of that material
CAT-NMC-001-C001-CC01   ← first coin cell from that coating
CAT-NMC-001-C001-SLP-01 ← first SLP from that coating
```


Prefix conventions:
- `CAT-` — cathode material
- `AN-` — anode material

- `SLP-` — single-layer pouch cell
- `CC-` — coin cell
- `MLP-` — multi-layer pouch cell

## Uploading cycling data

1. Navigate to **Tables → Upload Cycling Data**
2. Enter the record ID of the cell the file belongs to (e.g. `CAT-NMC-001-C001-CC01`)
3. Upload a BioLogic `.mpr` file

Once uploaded, the cell's card page, lineage card, and the graph quick-view panel will all show:
- Capacity fade chart (discharge capacity per cycle)
- Coulombic efficiency per cycle
- Voltage vs. capacity curves, selectable by cycle number

Cycling data can also be explored directly from the graph page without navigating away.
